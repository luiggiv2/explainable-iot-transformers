- **Dataset(s)**: Self-generated lab traffic captures (confirmed via full-text PDF). Nmap scan types actually run experimentally: TCP SYN scan (`-sS`, Nmap's default) and TCP Connect scan (`-sT`), each executed as `-F` (top 100 ports), default (top 1000 ports), `--top-ports 5000`, and `-p-` (all 65,535 ports) — 8 commands total, all issued from machine-1 against machine-2. The paper also *describes* (but does not experimentally run) six further scan types detectable via context-based signatures: Xmas (`-sX`), FIN (`-sF`), Null (`-sN`), ACK (`-sA`), Window (`-sW`), and Maimon (`-sM`) scans — no UDP scan (`-sU`) is used or discussed beyond one line noting Nmap's `-sSU` combined-scan option exists. **Testbed topology**: two-VM lab built on VMware Workstation 17 Pro. Machine-1 (scanner, IP 192.168.15.1): Windows 11 host running Nmap/Zenmap v7.93 and Wireshark v4.0.10. Machine-2 (target VM, IP 192.168.15.155): Windows 7 (chosen to match the OS used in EC-Council CEH v11 courseware). Wireshark capture filter restricted to `host 192.168.15.1 and host 192.168.15.155`; captured traffic exported to CSV and analyzed in Python (NumPy/Pandas/Matplotlib) via Jupyter. For the Nmap-vs-Metasploit fingerprinting comparison, a third machine (192.168.15.128) ran Metasploit's `auxiliary/scanner/portscan/syn` module against the same target.
- **Models / Methods**: Packet-level feature analysis; introduces the concept of an "Indicator of Scan (IoS)" — engineered indicators based on source-port behavior, destination-port distribution/statistics, and timing/inter-arrival attributes — used both to flag scan traffic and to fingerprint which scanning tool produced it (Nmap vs. Metasploit). No detection classifier is actually built/trained; the paper is a descriptive/characterization study only (confirmed via full text — this is explicitly deferred to future work).
- **Key metrics reported**: Confirmed via full-text Table 2 (traffic size/duration) and Table 1/3 (port-count and statistical measures). Table 2 — SYN scan, top 1000 ports: 117 kB total traffic, 2093 packets, 22.39 s duration; Connect scan, top 1000 ports: 247 kB, 4116 packets, 44.28 s; SYN scan, all ports: 8 MB, 135,199 packets, 66.7 s; Connect scan, all ports: 16 MB, 270,856 packets, 2858 s (~47.6 min) — illustrating that TCP Connect scans generate roughly 2x the traffic/duration of SYN scans at matched port counts, and scale far worse at full-port-range scans (43x the duration of SYN for all 65,535 ports). Table 1 — count of unique source ports used by the scanner: SYN+top100→1, SYN default→2, SYN+top5000→2 (source ports stay ~constant for SYN scans); Connect+top100→293, Connect default→2020, Connect+top5000→15,229 (source-port count scales roughly with destination-port count for Connect scans, since each requires a full three-way handshake). Table 3 — destination-port statistical measures for SYN scans: top-1000-ports mean=8634.85, median=3720, mode=1, SD=13,448.48, range 1–65,389. Qualitatively: source-port count is a reliable fingerprint distinguishing SYN vs. Connect scans; Metasploit's default port-selection is strictly ascending while Nmap's is pseudorandom — a clean tool-fingerprinting signal.
- **XAI method (if any)**: None.
- **Relevance to our RQs**: Feeds RQ2 (reconnaissance ground truth) by reinforcing that destination port alone is insufficient — timing/inter-arrival and source-port allocation patterns are also diagnostic — and feeds RQ3 by raising a concrete, citable caution: different scan tools leave distinguishable fingerprints (e.g., ascending vs. pseudorandom destination-port order, source-port count scaling), so a Reconnaissance class built from a single tool (CICIoT2023 uses nmap/fping/vulscan) may carry tool-specific artifacts rather than generic scanning signal, which is directly testable against our model's attributions.
- **Stated limitations**: Not presented as an explicit "Limitations" subsection (confirmed via full text — the paper has no such section), but the Conclusion & Future Work section (Section 4) reveals the study's real scope constraints: only a single attacker/target host pair was used (Windows 11 attacker → Windows 7 target VM, chosen to match CEH courseware rather than a currently-common OS); only 2 of the 8 discussed Nmap scan types (SYN, Connect) were empirically executed, with Xmas/FIN/Null/ACK/Window/Maimon scans and any UDP scan left untested; no actual scan-detection classifier was built or evaluated — the paper characterizes candidate "Indicator of Scan" features only. The authors explicitly defer to future work: "a scan detection system will be built based on the mentioned features in this paper," with "experiments... made on more widely used targets with OS windows 10 and 11."
- **Quotable finding (paraphrased)**: Beyond which ports are targeted, the timing behavior and source-port allocation of scan packets differ measurably by tool, implying that "reconnaissance" traffic generated with a single scanner in a lab or benchmark dataset may reflect that tool's specific fingerprint rather than scanning behavior in general.
